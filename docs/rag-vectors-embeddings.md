# RAG, Vectors, and Embeddings

As backends increasingly integrate LLMs (Large Language Models), a new set
of concepts has become part of everyday backend work: embeddings, vector
search, and Retrieval-Augmented Generation (RAG) — the exact pattern this
knowledge base assistant itself is built on.

## Embeddings

An embedding is a numeric vector representation of a piece of text (or
image, audio, etc.) that captures its semantic meaning. Texts with similar
meaning end up as vectors that are close together in this vector space,
even if they don't share the same words — e.g. "car" and "automobile"
would have similar embeddings despite no shared characters. Embeddings are
generated by a trained embedding model, and typically have hundreds to
thousands of dimensions.

## Vector similarity search

Once text is converted to embeddings, finding "similar" content becomes a
math problem: measure the distance or angle between vectors. The most
common metric is **cosine similarity** — how closely two vectors point in
the same direction, regardless of their magnitude. Given a query's
embedding, a vector search finds the stored embeddings with the highest
similarity score, i.e. the most semantically related content.

## Vector databases

For a handful of documents, brute-force comparing a query's vector against
every stored vector (as this project does) is fine. At scale — millions of
vectors — that becomes too slow, so purpose-built **vector databases**
(e.g. Pinecone, Weaviate, Qdrant, Milvus) or vector-search extensions for
existing databases (e.g. pgvector for PostgreSQL) use specialized indexing
structures (like HNSW graphs) to find approximate nearest neighbors much
faster than checking every vector.

## Retrieval-Augmented Generation (RAG)

RAG combines vector search with an LLM to ground the model's answers in
specific, real data rather than relying solely on what the model memorized
during training:

1. **Retrieve**: embed the user's question, vector-search a knowledge base
   for the most relevant chunks of text.
2. **Augment**: insert those retrieved chunks into the prompt sent to the
   LLM, as context.
3. **Generate**: the LLM generates an answer using that provided context,
   typically instructed to rely on it rather than outside knowledge.

## Why RAG matters

- **Reduces hallucination**: the model answers from real, retrieved text
  rather than guessing from training data, which may be outdated, generic,
  or simply wrong for a specific domain.
- **No retraining needed**: unlike fine-tuning a model on new data, RAG
  lets you update the knowledge base (add, remove, edit documents) and the
  system immediately reflects that — no expensive model retraining.
- **Source attribution**: because you know exactly which chunks were
  retrieved, answers can cite where information came from, letting users
  verify claims (as this project's assistant does).
- **Works with smaller, local models**: since the model doesn't need to
  have memorized the answer, a smaller model with good instruction-following
  can perform well on domain-specific Q&A when paired with good retrieval —
  relevant to running models entirely on-device (see Microsoft Foundry
  Local, which this project's real backend uses).
